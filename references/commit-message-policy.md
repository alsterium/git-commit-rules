# Commit Message Policy

このリファレンスは、`git-commit-rules` がメッセージを生成するときに使う詳細規約である。リポジトリ固有の規約があればそちらを優先する。

## ヘッダー

```text
<type>(<scope>): <日本語の短い命令形 summary>
```

`scope` は原則付与する。次の順で、差分の中心を最も正確に表す scope を選ぶ。

| 差分の中心 | scope の候補 |
| --- | --- |
| ユーザー向け機能 | 機能名、画面名、ドメイン名 |
| パッケージ・モジュール | パッケージ名、モジュール名 |
| API・サーバー層 | `api`、`server`、対象サービス名 |
| UI・クライアント層 | `ui`、`web`、`mobile`、対象画面名 |
| テスト・ドキュメント | 対象機能。対象がない場合は `test` または `docs` |
| CI・ビルド・開発設定 | `ci`、`build`、`config` |
| リポジトリ全体 | 意味のある scope がなければ `repo` |

scope は機械的に `misc` とせず、差分の説明に役立つ安定した名称を選ぶ。リポジトリ規約が scope 省略を定めている場合だけ `<type>: ...` を使う。

## type の選択

| type | 用途 | summary の例 |
| --- | --- | --- |
| `feat` | 新しい利用者向け能力 | `請求書の下書き保存を追加する` |
| `fix` | 誤動作や不具合を修正 | `期限切れトークンを拒否する` |
| `refactor` | 振る舞いを変えない構造改善 | `認証処理をサービス層へ移す` |
| `docs` | 文書だけを変更 | `API 利用手順を更新する` |
| `test` | 独立したテスト追加・整理 | `検索条件の境界値を追加する` |
| `chore` | 雑務、保守、依存更新 | `開発用スクリプトを整理する` |
| `style` | 振る舞いに影響しない書式 | `インポート順を統一する` |
| `perf` | 性能改善 | `一覧取得のクエリを高速化する` |
| `build` | ビルド・依存・パッケージング | `本番ビルドの依存を更新する` |
| `ci` | CI/CD 設定 | `テストジョブに型チェックを追加する` |
| `revert` | 既存コミットを取り消す | `不正なキャッシュ変更を取り消す` |

新機能の追加に伴う実装と直接の回帰テストは通常 `feat` の同じコミットにする。不具合を直す回帰テストと修正も通常 `fix` の同じコミットにする。テストや文書が独立した目的なら `test` や `docs` に分ける。

## summary

- 日本語の短い命令形にする。例: `認証エラーを分類する`、`設定例を追加する`。
- 72 文字以内にする。ヘッダー全体も短く保つ。
- 末尾に句点、`。`、`!`、`！` を付けない。破壊的変更の `!` は type/scope の直後にだけ置く。
- 実装詳細の羅列ではなく、利用者・保守者にとっての目的を表す。
- 「作業」「対応」「修正」だけの曖昧な表現を避ける。対象と動詞を含める。

## 本文

本文は常に次の三つの見出しを、この順序で含める。各見出しの下には少なくとも一つの具体的な説明を書く。

```text
変更:
- 期限切れトークンの検証を認証ミドルウェアに追加する

理由:
- 期限切れ後も保護 API に到達できる経路を閉じるため

検証:
- `npm test -- auth`: 成功
- `npm run lint`: 成功
```

`検証:` には実行コマンドと結果を書く。テスト、Lint、型チェック、ビルドを実行できないときは、未実行の理由を明記する。失敗していても安全な状態でユーザーの目的に沿ってコミットする場合は、失敗を成功と書き換えず、次のように記録する。

```text
検証:
- `npm test`: 既存の環境依存テスト 1 件が失敗。今回の差分とは無関係として残課題に記録
- `npm run lint`: 成功
```

## 破壊的変更

破壊的変更はヘッダーと本文の両方で表す。

```text
feat(api)!: 認証レスポンス形式を統一する

変更:
- 旧形式の `user` フィールドを `account` に置き換える

理由:
- クライアント間で異なる認証モデルを統一するため

検証:
- `npm test -- api`: 成功

BREAKING CHANGE: `user` は廃止し `account` を返す。利用者は v2 のレスポンスへ移行する。
移行手順: クライアントの参照先を `response.account` に変更してからデプロイする。
```

影響を受ける利用者、互換性が壊れる点、移行手順が決められない場合はコミットを停止する。単なる内部変更を過剰に breaking としないが、公開 API・設定・DB schema・CLI 引数などの互換性を確認する。

## 例

```text
feat(billing): 請求書の下書き保存を追加する

変更:
- 下書き請求書を保存する API と画面操作を追加する

理由:
- 入力途中の請求内容を後から再開できるようにするため

検証:
- `npm test -- billing`: 成功
- `npm run typecheck`: 成功
```

```text
fix(auth): 期限切れトークンを拒否する

変更:
- 有効期限を過ぎた JWT を認証失敗として扱う

理由:
- 期限切れ後も保護 API に到達できる不具合を修正するため

検証:
- `npm test -- auth`: 成功
```

```text
docs(api): 認証エラーの利用手順を更新する

変更:
- 401 と 403 の使い分け、再認証手順、応答例を追記する

理由:
- API 利用者が復旧方法を判断できるようにするため

検証:
- Markdown lint: 成功
```

```text
refactor(core): 設定読み込みを責務ごとに分割する

変更:
- 環境変数の解析と既定値の適用を別モジュールへ分離する

理由:
- 設定検証を単独でテストしやすくするため

検証:
- `npm test`: 成功
- `npm run typecheck`: 成功
```
